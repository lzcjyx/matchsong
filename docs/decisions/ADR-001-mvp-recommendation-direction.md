# ADR-001: MVP 推荐方向 —— 音域推荐

- **状态：** Accepted
- **日期：** 2026-07-30
- **决策人：** Coding Agent（M-1.6）
- **关联文档：** `docs/experiments/mvp-technical-decision.md`、`docs/research/product-opportunities.md`

## 背景

PLAN.md §2.1 将 MVP 定位为"基于用户稳定演唱音区、舒适音区、音高稳定性和歌曲演唱负担的可解释歌曲推荐"，并禁止无研究依据的音色/嗓音类型绝对结论。M-1 需要确认该方向是否可行，或是否应改为音色推荐/综合推荐。

## 决策

**MVP 采用音域推荐（方向 B）：**

1. 核心输入：用户稳定最低音、稳定最高音、舒适音区、音高轨迹稳定性 + 歌曲最低音/最高音/主旋律音区/高音持续时间/跳进难度/调性 + 用户偏好；
2. 输出：可解释的歌曲适唱度推荐（含推荐理由与升降调建议）；
3. **MVP 不需要后端**：全部核心流程（录音 → 音高分析 → 音域统计 → 推荐）在端侧完成；
4. **MVP 不默认保存原始音频**：仅保留派生特征（音高轨迹、音域统计、质量指标）；原始录音的保存/上传需用户明确同意；
5. **MVP 不引入 TFLite / 端侧模型**：音域分析用纯 DSP（YIN）即可满足。

## 理由

1. **可解释性**：音域推荐的全部依据是客观可测物理量，能回答"为什么推荐这首歌"；
2. **端侧可行性已实测**：M-1.5 Spike 证明 YIN 纯 Kotlin 在合成信号上 <0.03% 误差、1ms/帧；
3. **差异化空隙**：竞品研究（product-opportunities.md）确认"唱几句后推荐适合音域的歌"存在但竞争不充分；
4. **风险最低**：不依赖无法验证的音色分类，不需要模型训练数据；
5. **隐私友好**：无后端 + 不保存原始音频，天然满足 PLAN §3.2 隐私要求。

## 后果

- **积极**：端到端可在无网络、无后端下工作；推荐可解释、可测试（歌曲音域与用户音域直接可比）；符合 PLAN 质量门禁的"可验证"要求。
- **消极**：不做音色/嗓音类型分析，可能让部分用户预期落空（"我的声音类型是什么？"）；需要谨慎的文案管理。
- **成本**：需要建立可验证的歌曲音域特征数据（M6）；舒适音区需产品化定义（M0 SPEC）。

## 备选方案与拒绝理由

- **A. 音色推荐**：拒绝。PLAN §2.1 禁止无依据的绝对化结论；端侧音色识别需模型，MVP 阶段无法验证准确率；竞品 AI 声乐教练已密集布局。
- **C. 综合推荐（音色+音域）**：推迟。依赖音色识别可靠性，作为 MVP 之后的演进方向（可在 SPEC 中预留扩展点）。

## 待复核条件

- 若 M5 真机人声实测证明 YIN 音域估计不可靠且无法改进 → 重新评估方向。
- 若竞品快速跟进且数据（曲库）成为瓶颈 → 评估后端/曲库合作。
